# Explore: Spec-Mode Agent-Driven Start

**Topic:** Rework the spec-mode entry so the agent proactively drives the conversation from the first turn, rather than both modes feeling identical at start. Informed by how Kiro structures SDD (framing question → phased workflow with approval gates).

**Started:** 2026-08-13

## Context

The user's premise entering this exploration: "spec and go mode are no different at the start." Code trace shows this is **not literally true** — `spec_mode` (lib.rs:733) auto-fires `grill-explore` when there's no open change: it injects the full grill-explore SKILL.md as a user turn with the literal body `"grill-explore"` (lib.rs:722, `grill_inject::build_prompt`) and sends it to the session. So the agent receives a first turn and should speak first.

The real gap is subtler: the opening turn is _skill instructions + the bare word "grill-explore"_, not a structured framing question. The agent must improvise its opener. Kiro, by contrast, asks a framing question first ("Feature or Bug?"), then drives Requirements → Design → Tasks with approval gates between phases.

Relevant existing specs/changes:

- `new-thread-mode-picker` — the Vibe/Spec inline picker that seeds mode at thread creation
- `vibe-spec-tabs` — spec changes open as read-only editor tabs in the Vibe shell
- `spec-reference` — linked-change chip behavior
- Stage derivation in `src/stage.ts`: exploring → proposing → ready_to_apply → implementing

## D1: Insert a baked-in framing menu between "pick Spec" and "agent runs"

- **Decision**: After the user picks "Spec" from the Vibe/Spec new-thread picker, a pop-up menu appears ("What would you like to spec out today?") with a couple of baked-in spec-type options. The agent does NOT run yet. The user picks an option, and THAT selection starts grill-explore — the agent then drives the conversation back and forth with the chosen framing as context.
- **Why**: Today both modes feel identical at start because spec-mode auto-fires grill-explore with the bare literal `"grill-explore"` as the user turn body (lib.rs:722), giving the agent no framing task. A baked-in framing menu gives the agent a concrete starting frame (like Kiro's "Feature or Bug?" question) before it speaks, so the agent's opener is structured rather than improvised.
- **Source**: user

## D2: The framing menu is baked-in UI, not agent-generated

- **Decision**: The first pass of the framing menu is static baked-in UI (hardcoded spec-type cards), not generated by the agent. The agent only runs after the user picks an option.
- **Why**: Running the agent to generate framing options would reproduce the same "weak opener" problem one level earlier; a baked-in menu is instant, predictable, and doesn't burn a turn on asking what the user already knows.
- **Source**: user ("This first pass should be baked in and not run the agent")

## D3: Three spec-type options — Feature / Bugfix / Other

- **Decision**: The framing menu offers three baked-in cards: "Feature" (new capability), "Bugfix" (diagnose + fix), and "Other" (open-ended — the user types their own framing instead of picking a structured category).
- **Why**: Feature and Bugfix cover the two dominant SDD forks (mirroring Kiro); "Other" is the escape hatch for anything that doesn't fit either mold (refactors, research, architecture work) without forcing a false category. Three options is still "a couple" in spirit and keeps the menu scannable.
- **Source**: user

## D4: Second inline card row, built with Mantine components

- **Decision**: Picking "Spec" from the Vibe/Spec picker replaces it with a second inline card row showing Feature / Bugfix / Other, rendered with Mantine components (`UnstyledButton` + `Paper`/`Card` from `@mantine/core`) rather than raw `<button>` + custom CSS. Same inline-not-modal posture as the existing picker.
- **Why**: The `new-thread-mode-picker` spec mandates inline, not modal; reusing the inline card-row pattern keeps the flow consistent. Mantine components are required per CLAUDE.md ("UI components only: Use Mantine components and Tabler icons exclusively"), and `Button`/`Group`/`Box` are already imported in App.tsx — adding `UnstyledButton`/`Paper`/`Card` follows the existing import idiom.
- **Source**: user

## D5: Choice becomes the user turn body (replaces the literal "grill-explore")

- **Decision**: `spec_mode` gains a `spec_type` parameter. `spec_mode_initial_prompt` passes it to `build_prompt` as the user turn body instead of the literal string `"grill-explore"`. So the agent receives `[grill-explore SKILL.md]\n\n---\n\nFeature` (or `Bugfix`, or the user's free text for "Other"). The injected SKILL.md still tells the agent how to explore; the body now tells it _what kind_ of thing to explore.
- **Why**: Smallest diff to the existing `spec_mode` → `build_prompt` path (one new parameter, one string substitution). Keeps the auto-fire behavior the user already has, just with a meaningful body. No new IPC command, no prompt-template machinery to maintain.
- **Source**: user

## D6: "Other" reveals an inline text field; agent runs on submit

- **Decision**: Picking "Other" reveals a Mantine `TextInput` inline below the three cards. The user types their custom framing, hits Enter, and that text becomes the user turn body sent to grill-explore. All three paths (Feature / Bugfix / Other) produce a framed auto-fire — the agent always speaks first; only the framing source differs (baked-in card vs. text field).
- **Why**: Keeps "Other" consistent with Feature/Bugfix — no path gets a worse opener. `TextInput` is already imported in App.tsx, so the inline field is a small Mantine addition that matches the inline-not-modal posture.
- **Source**: user

## D7: spec_type is framing context only — no different artifact structure

- **Decision**: The spec_type (Feature/Bugfix/Other) is framing context for the agent's opening turn only. It does NOT change the OpenSpec artifact structure — Palisade's grill flow always creates the same set (proposal.md, design.md, spec.md, tasks.md, decisions.md). There is no bugfix.md variant to wire up.
- **Why**: Kiro differentiates Feature Specs (requirements.md) from Bugfix Specs (bugfix.md) at the file level, but Palisade's grill flow is type-agnostic — the artifacts are the same regardless of whether the change is a feature or a bugfix. The spec_type just helps the agent ask better framing questions.
- **Source**: codebase (openspec/changes/ structure, grill flow)

## D8: No-executor behavior is unchanged — framing menu shows, agent silently doesn't fire

- **Decision**: The framing menu is UI-only and shows regardless of executor availability. If no executor is detected (preflight fails), the agent silently doesn't fire — same as today's `spec_mode` behavior (lib.rs:743 checks `preflight_for_harness(...).selected.is_some()` before starting a session). No new error surface is introduced.
- **Why**: The framing menu is a frontend interaction before `specMode` is called; the executor check happens inside `spec_mode` after the choice is made. Adding a pre-check in the UI would duplicate the backend's preflight logic.
- **Source**: codebase (lib.rs:743)

## D9: Framing menu appears on both spec-mode entry paths

- **Decision**: The framing menu appears whenever spec mode is entered with no open change, on both entry paths: (1) the new-thread Vibe/Spec picker (`onPickMode("spec")`, App.tsx:1603) and (2) the composer Spec/Go toggle (`onSpec`, App.tsx:2002). Both paths show the Feature/Bugfix/Other cards before calling `api.specMode()`.
- **Why**: The weak-opener problem exists on both paths equally. Leaving the composer toggle with the bare "grill-explore" body means users who switch an existing go-mode thread to spec mode still get the improvised opener. The diff is the same — `onSpec` shows the framing menu before calling `specMode`, same as `onPickMode`.
- **Source**: user

## D10: spec_type is silently ignored when a change already exists

- **Decision**: `spec_mode` accepts `spec_type` but `spec_mode_initial_prompt` only uses it when `open_spec_change_name.is_none()`. If a change exists, `spec_type` is silently dropped — same as today's no-auto-fire behavior. No error path.
- **Why**: The frontend already gates the framing menu on "no open change" (D9), so the backend never receives `spec_type` when a change exists in practice. An error path (B) would be dead code that complicates the IPC contract. Silently ignoring matches the existing `spec_mode_initial_prompt` pattern.
- **Source**: user

## D11: spec_type persists on ThreadMeta

- **Decision**: Add a `spec_type: Option<String>` field to `ThreadMeta` (store.rs:189). The chosen spec_type (Feature/Bugfix/custom text) is stored on the thread and persists across mode switches and app restarts. When re-entering spec mode with no change, the stored spec_type is reused — the framing menu is NOT re-shown.
- **Why**: The spec_type gives context to the agent throughout the spec lifecycle, not just the opening turn. Persisting it means the framing survives session restarts and agent handoffs, and the user isn't re-prompted for a choice they already made. Old thread records get `None` via serde default (no migration needed).
- **Source**: user

## D12: Re-inject spec_type on agent handoff only, not app restart

- **Decision**: When a new spec-mode session starts via agent handoff (different agent, transcript rebuilt with 100k budget per lib.rs:584), re-inject the stored `spec_type` as the first turn body if `open_spec_change_name` is null. On app restart with the same agent, the full message history is reloaded (including the original first turn with the spec_type body), so no re-injection is needed.
- **Why**: On handoff the transcript may be truncated, dropping the original framing turn — the new agent would lose the spec_type context. On same-agent restart the full history is intact, so re-injecting would duplicate the framing turn. Targeting only the handoff path covers the gap without duplication.
- **Source**: user

## D13: Framing menu has a back button to return to Vibe/Spec picker

- **Decision**: The framing menu includes a "Back" affordance that returns to the Vibe/Spec picker. The user hasn't committed to a spec_type yet — they can still change their mind to "Go" instead. Implementation: `setNewThreadPicker(true)`, hide the framing menu.
- **Why**: The framing menu is a sub-step of the new-thread picker, not a separate flow. The user is still deciding what kind of thread to create. A back button is cheap (one state toggle) and prevents the dead-end feeling of "I picked Spec but I meant Go."
- **Source**: user

## D14: Card copy — bold title + one-line description

- **Decision**: The three spec-type cards use the same pattern as the existing Vibe/Spec cards (bold title + one-line description). Copy:
  - **Feature**: "Build something new — a capability, screen, or integration that doesn't exist yet."
  - **Bugfix**: "Diagnose and fix — trace a broken behavior to its root cause before changing code."
  - **Other**: "Open-ended — describe your own framing and the agent will explore from there."
- **Why**: Matches the existing Vibe/Spec card pattern and gives enough context to pick correctly without being verbose. "Other" explicitly tells the user they'll type their own framing, setting expectations for the TextInput.
- **Source**: user

## D15: "Other" text field — Enter-to-submit, contextual escape link

- **Decision**: Picking "Other" reveals a Mantine `TextInput` that fires on Enter (no submit button). Below the field, a small "or pick a different type" link returns to the three cards. Placeholder: "Describe what you'd like to spec out..."
- **Why**: Enter-to-submit matches the chat composer's keyboard-first feel — the user is about to enter a chat flow. The contextual escape link is lighter than relying on the top-level Back button (D13) — it's right below the field, not remote. A submit button would be redundant when Enter works and would clutter the inline layout.
- **Source**: user

## D16: Amend the existing new-thread-mode-picker spec

- **Decision**: This change amends the existing `new-thread-mode-picker` spec rather than creating a new spec. The requirement "Selecting 'Spec' SHALL create a thread and set its mode to `spec`" is amended to include the framing menu as an intermediate step. The spec_type persistence (D11) and re-injection-on-handoff (D12) become requirements in the same amended spec.
- **Why**: The framing menu is a direct modification of the picker's "Selecting Spec" scenario — the user's interaction changes from "creates thread immediately" to "shows framing menu first." That's an amendment to an existing requirement, not a new capability. Two specs covering one flow would create confusion about which spec owns the "what happens when you pick Spec" behavior.
- **Source**: user

## D17: Empty "Other" submission is disabled

- **Decision**: The "Other" TextInput does not fire on Enter when the field is empty (or whitespace-only). The user can't proceed until they type something. Mantine's `error` prop or a length check signals "describe what you'd like to spec out."
- **Why**: The entire point of the framing menu is to give the agent a concrete starting frame. Allowing an empty submission reintroduces the weak-opener problem for the "Other" path. Disabling submit when empty is a one-line check (`if (!otherText.trim()) return;`).
- **Source**: user

## D18: TDD vertical slices, riskiest first

- **Decision**: Test strategy is TDD vertical slices (failing test → implement → verify), same as the fim-completion change. Riskiest first: (1) Rust IPC plumbing — `spec_mode` accepts/uses `spec_type`, `ThreadMeta` serialization with new field + backward compat, handoff re-injection; (2) TS UI — framing menu rendering, card clicks, "Other" TextInput, empty-submit prevention, back button, state flow (no orphan threads).
- **Why**: Global rules mandate TDD with vertical slices. The Rust changes aren't trivial — `ThreadMeta` serialization affects the append-only store (backward compat with old records), and the handoff re-injection (D12) has a subtle condition (only on handoff, not same-agent restart). These are the riskiest parts and must be tested first.
- **Source**: user

## D19: Thread created after spec type is picked, not before

- **Decision**: The framing menu shows without creating a thread. The thread is only created when the user commits to a spec type (Feature/Bugfix/Other submit). If the user backs out to the Vibe/Spec picker, no orphan thread is left. State flow: `newThreadPicker` → pick "Spec" → `specTypePicker` → pick spec type → `createThread` + `specMode(id, specType)`. For the composer toggle path (`onSpec`), the thread already exists, so it goes straight to `specMode(thread.id, specType)`.
- **Why**: The framing menu is part of the new-thread picker, which already shows without a thread. Creating the thread only on spec-type commit prevents orphan threads from backing out.
- **Source**: user
